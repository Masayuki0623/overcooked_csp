# 三つの層と、直すときの決まり

不具合を1つ直すたびに例外処理を足していくと、いつの間にか「CSP として
何を解いているのか」が変わってしまう。どこを直すかを迷わないための線引き。

## 層

### A. 計画（CSPAgent.solve_csp_scheduling）

盤面の状態を入力に、**いま残っている工程の順番と担当**を決める。

- 目的: `makespan × (工程数×1000) + 各工程の終了時刻の和`
  makespan が辞書式に優先される。同点のときだけ担当替えの罰が効く。
- 制約: 工程の前後関係 / 鍋・ミキサー・まな板の占有（重ねない）/
  移動時間 / skip_budget（指示の前に挟んでよい他工程の数）
- 締切は**罰**であってハード制約ではない。1件間に合わないだけで
  解が無くなると、残り全部の段取りまで壊れる。

**入れてよいのは、その瞬間の盤面から決まる事実だけ。**
実時間の履歴（何秒前に何があったか）を制約に混ぜない。混ぜると、
同じ盤面でも過去しだいで別の解が出る＝再現できなくなる。

### B. 実行（TaskAgent）

計画が決めた1つの工程を、**この手の一歩**に落とす。経路・持ち替え・
置き場所の選び方はここ。盤面を見て毎回決め直す、使い捨ての判断。

### C. 番人（_watch_progress / blocked_tasks）

**計画どおりに進んでいないこと**を見つける。CSP は「相手が材料を
持ったまま動かない」といった現実を知らないので、その食い違いを
拾うのがここの仕事。

## 決まり

1. **例外は B か C で処理する。A にタスクを隠さない。**
   「この工程は今できない」を A から取り除くと、makespan の見積もりから
   も消え、目的関数の意味が変わる。計画には残したまま、実行側が
   別の工程を先にやる。

2. **C の判断を A の制約へ渡さない。**
   C は時計で動く（何秒進まなかったか）。A に渡すと、実時間の履歴が
   制約になる。→ `tests/spec_csp_contract.py` が見張る。

3. **「できない」は盤面から決める。時計で決めない。**
   相手が材料を持っている・仕切りの向こうにある、はその瞬間の盤面から
   分かる。分かるものにカウントダウンを使わない。盤面が変われば次の
   判断で自然に戻る。

4. **指示（実験の独立変数）を黙って消さない。**
   実行できなくなった指示を棄却するのは仕方ないが、棄却したことは
   必ず記録に残す（`web_instructions.csv` の「指示の結末」）。

5. **仕様を変えるときは、先に `tests/spec_csp_contract.py` を直す。**
   テストが落ちたら「仕様が変わった」の合図。意図した変更なら表の方を
   直してから進める。意図していなければ、それが不具合。

## いま満たせていないところ

- `_assignable_agents` が `blocked_tasks`（30秒のカウントダウン）を見て
  いて、その結果が仕切りのある地図で `model.Add(is_a1[i] == ...)` に
  なる。決まり 2 と 3 に反する。
  実害: 材料がそろっても、諦めた直後だと 30 秒間その工程を取れない
  （報告 20260927_211043。30.0秒に材料がそろったのに、25.6秒に諦めた
  ぶんの 30 秒が解けず、42.2秒の終了まで鍋に入らなかった）。
